# 海盐县人民医院 · 软件问题登记程序
## 增量升级包 v1.18 — 部署说明

### 一、本次变更要点

**多机构（多院区）支持**：一套程序、一个数据库，支撑多家医院 / 院区各自独立使用。

- **机构数据隔离**：问题登记、用户、消息通知、聊天、值班表、操作日志、系统设置**全部按机构隔离**，机构之间互相看不到对方的任何数据（跨机构按 id 读取一律返回「不存在」）。
- **机构切换器**：当账号可访问多个机构时，**内容区右上角**出现「当前机构」入口，一键切换。自 **v1.18.9** 起该位置**恒定显示**「当前机构 + 机构名」：能切换的渲染为**蓝色可点控件（带下拉箭头）**，只能访问一个机构的渲染为**灰色只读标签（带「仅此一个」小标、无箭头、不可点）**，因此**每个登录的人都能一眼看到自己在哪个机构**。
- **机构管理**（新增左侧菜单，**仅平台管理员可见**）：新建机构 / 改名 / 启用停用 / 删除；**成员管理**（把账号加入机构、设置其「机构内角色」、移出机构）。
- **角色按机构独立**：同一账号在不同机构可以拥有**不同角色**；权限判定以「当前机构」的角色配置与该账号在该机构内的角色为准（**平台管理员除外** —— v1.18.10 起它在全部机构恒为管理员，见下）。
- **平台管理员**：跨机构管理角色，在「用户管理」中授予 / 取消（用户名字后带「平台管理员」标记）。首次启动时系统会自动把**最早的一个管理员**提升为平台管理员，避免升级后无人能管理多机构。**v1.18.10 起，平台管理员在全部机构的有效角色恒为「管理员」**——即使某机构里给它配的是别的角色（界面上显示为「管理员 · 固定」，不可改）。
- **公司用户 / 院方用户（v1.18.12）**：每个账号带一个「用户类型」属性 —— **院方用户**（默认，只能属于一个机构）与**公司用户**（可同时归属多个机构，例如设备厂商驻点人员）。**公司用户的创建、类型切换与多机构分配仅平台管理员可办**；机构管理员看不到相关入口、创建的永远是院方用户。详见第九节 v1.18.12。
- **排班跨机构同步（v1.18.13，v1.18.18 升级为镜像同步）**：值班表新增「跨机构同步」入口（**仅平台管理员可见可用**）—— 可把本机构某时间段的排班**推送**到多选的其他机构，或把其他机构的排班**拉取**到本机构（单次最多 20 个机构）。**v1.18.18 起为「带来源标记的镜像同步」**：同步=与源机构对齐（新增 / 更新 / 移除上次同步产生的条目），**手工排的班不受影响**。详见第九节 v1.18.13 与 v1.18.18。
- **聊天撤回 / 复制 + 会话移除（v1.18.14)**：聊天消息支持**撤回**（悬浮气泡出现「复制 / 撤回」按钮）与**复制**；左侧会话列表支持**移除** —— AI 会话=删除（下次发消息自动新建），同事会话=退出（其他成员不受影响）。详见第九节 v1.18.14。
- **用户管理界面调整（v1.18.15）**：用户列表的「类型筛选」从下拉框改为**二级 sheet 页标签**（全部 / 院方用户 / 公司用户），与页头一级 sheet 页（用户列表 / 角色与权限）风格统一、层级分明；筛选行为与展示结果完全不变。**纯前端改动，覆盖 `frontend/dist` 后无需重启后端**。详见第九节 v1.18.15。
- **处理人候选改为机构公司用户派生（v1.18.16）**：系统设置的「处理人候选名单」**手工维护界面已移除**；问题登记 / 编辑 / 指派与值班表的处理人下拉，改为自动列出**本机构花名册中的公司用户**（实时派生、按姓名排序，候选结构 { empId, name, phone } 不变：工号=登录账号、电话恒为空）。历史手工名单**仅留档、不再生效**；机构暂无公司用户时下拉为空，去「用户管理」创建公司用户、或「机构管理 → 成员管理」分配到本机构后**自动出现**。**软件系统候选名单的维护不受影响**。详见第九节 v1.18.16。
- **用户增加联系电话（v1.18.17）**：新建账号弹框新增选填的「**联系电话**」输入框（≤20 字符）；用户列表新增「**电话**」列（未填显示 —）与行内「**改电话**」按钮。电话为**账号级字段（与密码同级）**：**平台管理员可改任意账号（含多机构公司用户），机构管理员仅限「仅属本机构」的账号**；修改写入操作日志且**电话脱敏**（保留前3后4，如 138****8026）。**值班表 / 处理人下拉自动带出所填电话**（v1.18.16 派生打通：公司用户填了电话，登记 / 排班表单与值班表即显示联系方式）。`app_user` 新增 `phone` 列（启动自动平滑加列）。详见第九节 v1.18.17。
- **排班同步升级为镜像同步（v1.18.18）**：跨机构同步从「跳过式复制」升级为**带来源标记的镜像同步**——把所选时段的排班与源机构**对齐**：源有目标没有的**新增**、同键条目内容有变化的**更新**、**上次同步产生**但源里已删除的**移除**；**手工排的班不受影响（不会被改也不会被删）**，重复同步幂等（全一致时提示「排班已一致，无需变更」）。`duty_schedule` 新增 `synced` 同步来源标记列（启动自动平滑加列，**存量条目自动视为手工、不受影响**）。详见第九节 v1.18.18。

**关于存量数据（升级后界面为什么没有任何变化）**

升级后首次访问会自动：
1. 创建「默认机构」（名称取 `backend/.env` 的 `DEFAULT_ORG_NAME`，缺省为「默认机构」）；
2. 把**全部存量用户**补进该机构（沿用其原角色）；
3. 把**原有全局系统设置**（系统名称、处理人名单、软件系统、角色与权限）**一次性复制**为该机构的机构级设置；
4. 指定平台管理员（见上）。

因此**单机构场景升级后，登录看到的数据、权限、系统名称与升级前完全一致**，无需任何人工干预；只是在此基础上多了「将来可以再加一个机构」的能力。

> v1.18.9 起，**内容区顶部会多出一行**（右上角显示「当前机构 + 机构名」，单机构时为灰色只读标签）。这是本次需求「每个用户登录都要知道自己登的是哪个机构」的直接结果：它**不改变任何数据、权限或系统名称**，只是把那行页眉改为恒常显示；单机构时该行不带下分隔线、行高也已压缩，视觉上尽量轻。

#### 关于「用户管理 / 系统设置是否每个机构独立」（已复核，结论如下）

| 事项 | 现状 | 说明 |
|---|---|---|
| 系统设置：系统名称、处理人名单、软件系统 | **按机构独立** | 存于机构级设置（mssql 表 `app_org_setting`，dev 存 `settings.json` 的 `__orgs`），互不影响 |
| 系统设置：角色与权限（含新增 / 改名 / 删除角色） | **按机构独立** | 每个机构一套角色表与权限矩阵，改 A 机构不影响 B 机构 |
| 用户管理：花名册 | **按机构独立** | 只列「本机构成员」；登记人下拉同理 |
| 用户管理：新建账号、改「机构内角色」 | **按机构独立** | 新建即自动加入当前机构；改角色只写机构成员关系，**不回写全局角色**（跨机构按 id 改角色 → 404） |
| 用户管理：重置密码 / 停用启用 | **账号级（全局）** | 密码与启停状态全系统唯一；v1.18.7 起限「平台管理员」或「本机构专属账号」，详见第八节 |
| 跨机构加入已有账号 | **平台管理员专办** | 入口在「机构管理 → 成员管理」；机构管理员在本机构内同名新建会提示「用户名已存在」 |

### 五、新增权限

- **本次不新增任何角色权限项**：原有菜单与功能权限的 key **完全不变**，无需在「系统设置 → 权限」里做任何勾选调整。
- 「机构管理」是**平台管理员专属入口**，不走角色权限体系（因为它本质是跨机构操作，放进任何单个机构的角色里都不成立）。
- 自 v1.18.2 起，它会在「用户管理 → 角色与权限 → 权限设置」弹框左栏的 **「平台级功能」分组**下显式列出（右侧标注「平台级」，**没有勾选框**，只说明授权方式）。这是**纯提示**，不产生任何新权限项、不改变任何角色的实际权限：
  - 「权限设置」配置的是**某个机构内某个角色**的权限（角色按机构独立存储）；
  - 而「机构管理」是**跨机构**操作 —— 若把它做成可按机构角色勾选，A 机构的管理员就能去管 B 机构，属于越权；
  - 因此它的授权入口固定为「用户列表 → 用户名后的『设为平台管理员』」。
- **行为变化（v1.18.3）**：**平台管理员在任意机构都能使用「用户管理」与「系统设置」**（此前在「自己不是成员的机构」里会按全局角色降权，导致这两个菜单消失、接口 403）。这是修复，不是新增权限项 —— 原有 key 与勾选配置一律不变。
  - 同时**新建机构时创建者会自动成为该机构成员（管理员角色）**，因此新机构从 1 名成员开始，不再是空机构。
  - 另外，**在某个机构里修改某成员的「机构内角色」，不再顺带改写他的「全局角色」**（此前会泄漏到其它机构）。
- 但请注意一个行为变化：**「系统设置」里的角色与权限现在按机构独立存储**。
  - 升级后：默认机构沿用你原先的全局配置（完全一致）；
  - 将来新建的机构：自动以「系统默认角色 / 权限」初始化，可由该机构的管理员自行调整，互不影响。
- **行为变化（v1.18.10）：平台管理员在全部机构一律按管理员角色生效**。
  - **不新增任何权限项**，原有权限 key 与勾选配置一律不变；变化的只是「平台管理员这个身份如何换算成有效角色」；
  - 修复前：`roleInOrg` 是「成员关系优先」，而升级时系统会把你的**全局角色**自动复制成默认机构的**成员角色** —— 平台管理员的全局角色往往只是「登记员」，于是他在**自己的医院**里被降权（真实案例：海盐县人民医院少了 审核通过 / 用户管理 / 系统设置 三个菜单，而同账号在海盐县中医院是管理员、菜单全开）；
  - 修复后：平台管理员不管在哪个机构、不管成员关系里存的是什么角色，**有效角色都是管理员**；「用户管理 / 机构管理」里他的角色会显示为「**管理员 · 固定**」（不可改，改了也不生效，索性不让改）；
  - **为什么可以这么做**：这条限制本来就不是安全边界 —— 平台管理员本就能在任意机构把自己或别人改成管理员；限制他只制造困惑、不产生约束；
  - **非平台管理员完全不变**：成员关系优先的原则依然成立，仍然可以「故意给某个普通成员配一个低权限角色」；
  - ⚠️ **需重新登录**：角色写在登录凭证里，升级后请**退出并重新登录**，菜单与接口权限才会按新规则计算。

### 六、升级步骤（推荐）

1. 在服务器**停止**当前运行的服务（任务计划禁用 / 结束 `HospitalIssueTracker`，或 `taskkill`）。
2. **备份**：现有 `frontend/dist`、`backend/src`，以及**数据库**（便于回滚）。
3. 按「二、文件清单」覆盖本包文件到对应位置（注意新增的 `backend/src/orgs/` 整个目录）。
4. 重新启动服务。
5. **所有账号退出并重新登录**（v1.18.10：角色写在登录凭证里，旧凭证仍按登录时的角色计算）。
6. **验证清单**：
   - 用原管理员账号登录 → 界面、数据、权限应与升级前**完全一致**；**唯一的视觉差异**是内容区右上角多了一枚机构标签（只有 1 个机构时是**灰色只读**形态，见下一条）；
   - **右上角机构条（v1.18.9）**：登录后**必定**能看到「当前机构 + 机构名」——
     - 只能访问**一个**机构（含全部单机构部署）→ 显示为**灰底细边的只读标签**，右侧带「**仅此一个**」小标，**没有下拉箭头、点它没反应**（它原本就不是按钮）；
     - 能访问**两个及以上**机构 → 显示为**蓝底、左侧带蓝色竖条、带下拉箭头**的可点控件，点开可切换；
     - 判断依据是「该账号**被授权访问几个启用中的机构**」——即机构成员关系，而不是某个单独的开关；只有 1 个机构时自然就没有可切换的目标；

### 八、已知限制（请留意使用边界）

- **通知为「扇出式」，不追溯**：全员广播在**发送时**为当时该机构的全部启用成员各写一条记录；**后来才加入该机构的账号看不到历史广播**。这与升级前的通知机制一致。
- **新建机构不复制业务数据**：新机构是空的（仅继承系统默认角色 / 权限与机构名）。**存量历史问题仍留在默认机构，不会自动分摊**到其它机构。
- **守卫规则**：至少保留一个启用中的机构；默认机构（ID 最小者）不可删除；不能把机构成员清空到 0 人；不能取消最后一个平台管理员。
- **导出**：Excel / CSV 导出内容自动限定为「当前机构」，与列表口径保持一致。
- **登录防爆破计数**为进程内存级（重启即清空），与升级前一致。
- **「账号」是全局的，密码与启停状态也是全局的（v1.18.7 起明确）**：同一个账号可在多个机构任职，但它只有**一套密码**、**一个启用状态**（这是 v1.18 的既定模型 —— 账号全局唯一，机构差异只体现在「机构内角色」）。因此：
  - **跨机构共有账号**的密码重置与停用 / 启用，只能由**平台管理员**操作（避免任一机构通过改密码/停用来接管该账号的其它机构权限）；
  - 只属于**单一机构**的账号，该机构管理员可自行重置密码、停用启用；
  - 各机构仍然可以**独立调整共有账号在「本机构内」的角色**（例如在 A 院是登记员、在 B 院是管理员），互不影响。
- **机构管理员不能把「已有账号」加进自己的机构**：成员指派入口（机构管理 → 成员管理）归平台管理员。若甲院同事已在本系统有账号、现在需要进乙院，请由**平台管理员**在「机构管理」里加入；机构管理员在本机构内用同名新建会提示「用户名已存在」。
- **「能不能切换机构」的判定口径（v1.18.9）**：右上角机构条是否可点，取决于**当前账号能访问几个「启用中」的机构**（即机构成员关系 + 平台管理员身份带来的全部机构）。
  - 只有 1 个 → 只读标签（灰色）；
  - ≥2 个 → 可切换控件（蓝色）。
  - **已停用机构不计入**：后端对切换目标为已停用机构会返回 `403 该机构已停用，无法切换`，若把它算进来就会出现「有下拉可点、点谁都被拒」的假入口。
  - 因此**不需要任何额外的权限开关** —— 「被授权访问第二个机构」这件事本身就只能在「机构管理 → 成员管理」里做到，那一步就是授权动作。
- **平台管理员的机构内角色是「固定」的（v1.18.10）**：平台管理员在**全部机构**的有效角色恒为内置管理员角色，**不按机构调整**。
  - 「用户管理」与「机构管理 → 成员管理」里，平台管理员那一行的角色显示为「**管理员 · 固定**」（说明文字，不是下拉框），并附 `storedRole`（库里实存的角色，tooltip 可见）供排查；
  - 通过接口把它改成别的角色会得到 **400**「平台管理员在全部机构固定为管理员角色…如需限制其权限，请先取消其平台管理员身份」；「加入成员」时选中的若是平台管理员，角色会被**自动纠正为管理员**并在返回里标 `coerced:true`（界面会提示）；
  - **非平台管理员不受影响**，成员关系优先、可任意按机构配角色；
  - ⚠️ 角色写在**登录凭证**里：授予 / 取消平台管理员、或改动任何人的机构内角色后，**对方需重新登录**才会按新角色计算接口权限（界面菜单会随 `/me` 立即变化，但接口要到重新登录才一致 —— 所以请重新登录）。

- **v1.18.5（2026-09-23）**：**修复「上传附件的中文文件名显示为乱码」**（问题附件与聊天附件同时生效）。
  - 现象：附件名显示成 `ä¼šè®®çºªè¦2026.pdf` 这类字符；下载另存为时文件名同样是乱码，只有扩展名（`.pdf`）还是对的。
  - 原因：上传是 `multipart/form-data`，文件名写在 HTTP 头 `Content-Disposition: ... filename="..."` 里。**浏览器发出去的是 UTF-8 字节**，而服务端解析库（`multer` → `busboy`）的 `defParamCharset` **默认值是 `latin1`** —— 它把这串 UTF-8 字节**逐个当单字节字符**读，于是每个汉字被拆成 2~3 个西欧符号，落库时存的就是这串乱码。**与数据库、浏览器、Chrome/Edge 版本无关，是解析侧的默认值问题。**
  - 修复（两层，缺一不可）：
    - ① **源头**：给 multer 传入 `defParamCharset: 'utf8'`，新上传的文件名从解析那一刻起就是正确的（连磁盘落盘用的扩展名也取自已修正的名字）；

  - **语义变化**：v1.18.13 的同步是「跳过式复制」——目标机构已有「同日同人」条目一律跳过，重复同步永远 copied=0，源里的改动与删除**传不过去**。本次按用户需求升级为**镜像同步（对齐）**：把所选时段的目标排班与源机构对齐，逐机构按「同日同人」键（有账号按账号、无账号按姓名）分四个分支处理：
    - **新增（copied）**：源有、目标没有 → 在目标创建（打 `synced=1` 来源标记，登记人=操作者）；
    - **更新（updated）**：同键条目内容（账号 / 姓名 / 备注，规范化后全等判断）不一致 → 用源内容更新目标。**更新不分 synced 标记**——v1.18.13 时代同步产生的无标记存量条目与手工条目都参与同键对齐（用户明确要求）；但对齐**不改变条目自身的 synced 标记**（手工条目被对齐后仍视为手工）；

    - **移除（removed，保守）**：目标中 **`synced=1`（上次同步产生）** 且源里已无该键的条目 → 删除。**`synced=0` 的条目（手工排班 / 复制周）永不被移除**，键不匹配时完全不动。
