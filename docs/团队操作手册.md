## 1. 概述

本手册说明团队如何基于 **GitHub** 协作开发「信息科登记问题程序」，覆盖：

- 代码托管、克隆、分支、提交、推送、Pull Request（PR）、合并
- 多人同时开发的同步与冲突处理
- AI 助手（WorkBuddy / CodeBuddy 等）如何自动完成上述流程
- 本机网络不稳定时的标准应对

目标：**任何人（含 AI）改动代码，都必须通过 PR 合并进 `main`，且合并前已同步远端最新代码，冲突由人确认。** 严禁直接把未同步的代码覆盖他人成果。

## 2. 环境准备

### 2.1 开发者本机

| 工具 | 用途 | 说明 |
|---|---|---|
| Git ≥ 2.40 | 版本控制 | 从 git-scm.com 安装，安装时选「Checkout as-is, commit as-is」或默认即可 |
| GitHub 账号 | 代码托管身份 | 由管理员（chengyaocai）邀请加入仓库 |
| 编辑器 | 编码 | VS Code / WebStorm 等任意 |
| Node.js 18+ | 运行后端 / 前端 | 见 `backend/package.json`、`frontend/package.json` |

### 2.2 网络说明（重要）

本机访问 GitHub 走公司/沙箱代理，**时通时断**（偶发 HTTPS 502、TLS 握手失败、DNS 超时）。

- **这不是故障，是常态**：clone / push / pull 失败（502 或超时）时，**自动重试 3~10 次，间隔 5~8 秒**即可，不要立即判定为无法连接。
- SSH 方式（`ssh.github.com:443`）在本环境握手卡死，**不可用**，一律用 HTTPS。
- `hosts` 文件在本机无写入权限，不要尝试修改。
- API 通道（`api.github.com`）相对更稳定，大文件/批量推送走 API（见 §9.4）。

### 2.3 首次凭据授权

首次 `git push` 会弹出 GitHub 登录窗口（Git Credential Manager 浏览器授权），点「Authorize」即可。凭据会被记住，后续推送无需重复登录。

## 5. 日常开发流程

### 5.1 分支策略

| 分支 | 用途 | 是否可直推 main |
|---|---|---|
| `main` | 稳定主干，生产对应版本 | ❌ 受保护，禁止直接 push |
| `feature/<功能名>` | 新功能开发 | ——（合并进 main） |
| `fix/<问题名>` | 问题修复 | ——（合并进 main） |

> 命名示例：`feature/v1.18.48-export-excel`、`fix/login-token-expire`

### 5.2 开始一个任务

```bash
git switch main
git pull --rebase origin main      # 先同步到最新
git switch -c feature/v1.18.48-xxx  # 开功能分支
# ... 编码 ...
```

### 5.3 提交规范

提交信息格式：`<类型>: <简要描述>`

| 类型 | 含义 |
|---|---|
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `docs` | 文档 |
| `refactor` | 重构（无行为变化） |
| `test` | 测试 |
| `chore` | 构建/杂项 |

示例：`feat: v1.18.48 导出增加工时汇总列`

每个提交只做一件事，标题即本任务目标。

## 6. 推送前必做：同步远端

**这是避免冲突覆盖的核心步骤。**

```bash
# 在 feature 分支上，推送前先同步 main
git fetch origin main
git rebase origin/main          # 把你的提交接到最新 main 之上
# 若出现冲突：见 §7
git push -u origin feature/v1.18.48-xxx
```

- 无冲突：rebase 自动完成，直接 push。
- 有冲突：Git 会暂停，按 §7 处理后再 `git rebase --continue`。

推送失败（502/超时）时重试（见 §9.3）。

---

## 7. 冲突处理（关键）

冲突发生于：你改的文件，远端 main 也被他人（或 AI）改了同一处。

### 7.1 人处理流程

1. `git status` 看冲突文件（标记 `both modified`）。
2. 打开文件，查找 `<<<<<<<`、`=======`、`>>>>>>>` 冲突块。
3. 与对方（或 AI）确认正确结果，手动编辑保留正确内容，删除冲突标记。
4. `git add <已解决文件>` → `git rebase --continue`。
5. 全部解决后 `git push -u origin feature/xxx`。

### 7.2 AI 协作模式（默认）

当由 AI 助手提交时，AI 会：

1. 执行 `git pull --rebase origin main` 自动同步。
2. 出现冲突时，**逐文件分析差异、给出合并建议，但不静默覆盖**——必须**由人确认**后再提交。
3. 给出冲突清单与建议，等你回复「按建议合并 / 保留某方」后再继续。

> 原则：AI 可自动处理无冲突的合并；**有冲突一律等人拍板**。

## 8. Pull Request 与合并

### 8.1 发起 PR

```bash
git push -u origin feature/v1.18.48-xxx
```

推送后 GitHub 会给出 PR 创建链接，或直接在仓库页面 New Pull Request。

PR 描述必须写明：

- **改动点**：做了什么
- **影响范围**：动了哪些模块 / 是否前后端都改 / 是否新增表字段
- **自测结果**：本地能否启动、主流程是否可用

### 8.2 评审与合并

| 角色 | 职责 |
|---|---|
| 开发成员 | 评审他人 PR，确认改动正确、无回归 |
| 管理员（chengyaocai） | 合并 PR、配置分支保护、管理成员 |

合并方式：**默认 `squash`**（把 feature 分支多个提交压缩为一条，保持 `main` 历史整洁）。

### 8.3 通过 AI 发起 / 合并

AI 助手可基于仓库凭据自动：建 PR、合并（squash）、打标签。你只需说：

- 「把这个改动提 PR」
- 「合并这个 PR」
- 「拉最新代码并合并冲突」

## 9. 故障排查

### 9.1 502 / 超时（最常见）

`fatal: unable to access '...github.com...': CONNECT tunnel failed, response 502` 或 TLS 失败。

→ **重试**。单次可能挂起无响应，超时可强制中断后重跑：

```bash
for i in $(seq 1 10); do
  git pull --rebase origin main && break
  sleep 8
done
```

大批量推送（首次全量 200+ 文件）建议走 API（§9.4），避免 git 协议长传输被代理掐断。

### 9.2 凭据失效

`remote: Invalid username or password` → 重新触发授权（删掉 Windows 凭据管理器里的 `git:https://github.com` 项，下次 push 会重新弹窗）。

### 9.3 `main` 拒绝直推

`remote: error: GH006: Protected branch` → 说明你在 `main` 上直接 push 被拒。改到 feature 分支，走 PR 合并。

### 9.4 大文件 / 批量推送走 API（管理员/AI 专用）

当 git push 反复失败（代理对 `github.com` 持续 502，单连接挂死），用 Git Data API 通道（`api.github.com` 稳定）：

脚本：`push_via_api.py`（位于 WorkBuddy 工作区 `.workbuddy/`）

```bash
cd <项目目录>
python push_via_api.py chengyaocai HospitalIssue main "feat: ...提交说明..."
```

原理：逐文件建 blob → 建树 → 建提交 → 更新分支引用。需本地已 `git commit` 且 GCM 中存有 github 凭据。

## 10. 版本管理

- **版本号唯一来源**：`frontend/src/version.js` 的 `APP_VERSION`（如 `v1.18.47`）。界面底部署名读取此常量。
- 每次发布新版本：同步更新 `version.js`、升级说明 `.md`、并在仓库打 tag。
- **打 tag**（指向 `main` 当前提交）：

```bash
git tag v1.18.48 && git push origin v1.18.48
# 或经 AI/API：python gh_api.py create_tag v1.18.48 <提交SHA>
```

- 升级说明：`release/hospital-issue-tracker-deploy-patch-v1.18/README-升级说明.md` 记录每个版本的功能、前后端、新表列、兼容性。

## 11. 分支保护（管理员配置）

建议仓库 Settings → Branches 配置：

- `main` 设为 Protected
- ☑ Require a pull request before merging
- ☑ Require approval（至少 1 人）
- ☑ Require status checks（如有 CI）
- ☑ Do not allow bypass

配置后，任何人都无法直推 `main`，强制走 §8 流程。

1. 管理员进入仓库 → **Settings → Collaborators → Add people**
2. 输入成员 GitHub 用户名，选权限（Write）
3. 成员接受邀请后，按 §4 克隆即可开发、建分支、提 PR

## 13. 发布流程（增量交付）

本项目采用**增量补丁**交付：每个版本聚焦单一功能变更，产出补丁包放入 `release/`。

1. 完成 feature 开发，PR 合并进 `main`。
2. 更新 `version.js` → 提 PR / 直接提交（紧随功能 PR 之后）。
3. 打 tag `vX.Y.Z`。
4. 在 `release/hospital-issue-tracker-deploy-patch-vX.Y/`（沿用既有补丁目录约定）产出增量文件，更新升级说明。
5. AI 按「工程师实现 → QA 全量回归」双角色检查，输出回归清单后再发布。
